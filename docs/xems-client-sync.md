# XEMS — синхрон клиент ↔ таблет ↔ сървър (1.1.202-ai)

Без таймери: всичко тръгва при събитие (push при събития, никакви периодични заявки).

## Кой е собственик на кои данни
| Данни | Собственик | Път | Посока |
|---|---|---|---|
| Часове | календарът (Acuity → Google Calendar или календарът на таблета) | Android Calendar | чете се на таблета; „+ Час“ пише в календара на таблета |
| Профил (име, контакт, пол, година, ръст, тегло, цел, колко спортува, зони за акцент, какво да се има предвид, медицински причини, бележка) | клиентът | PWA → `POST /v1/profile` → `client_inbox` → таблетът тегли `POST /v1/inbox` | клиент → таблет |
| Тренировки и прогрес | таблетът | веднага след записа на тренировката (`wearable/CardPublisher`: страницата на отчета без екран → `POST /v1/card` → `/c/<id>`); PWA пита `POST /v1/card/find` само при влизане в PWA около тренировка (най-много веднъж в минута; няма бутони за опресняване и фоново опресняване; списъкът с часове се опреснява при влизане и след резервация) (до 4 ч след началото на часа, докато картонът не е обновен след него); неотворен нов отчет → прозорец „Отчетът ти е готов“ при отваряне | таблет → клиент |
| Данни за анализа на тренировката | таблетът | 2 s след записа (`wearable/SessionUploader` → `POST /v1/session`): резюме + посекундният запис, gzip на таблета (≈5–30 KB), в D1 `session_records`; пълен запис за последните 12 тренировки на клиент, само резюме за по-старите (до 600); догонва по 6 стари; само за клиент с имейл/телефон | таблет → клиент; `/r/<cardId>` (същият `session-report.html`, кратък вид) взима всичко с **една** заявка `GET /v1/history/<cardId>` и разархивира в браузъра; отваря се от „Моят прогрес“ и от бутона „Анализ на тренировката“ в картата |

Всяко поле има един собственик — няма двупосочно сливане и конфликти.

## Сливане на профил на таблета (`widget/XemsClientSync`)
- Клиентът се търси по имейл, после по последните 9 цифри от телефона; няма го → нов клиент.
- Поле се взима от профила, ако на таблета е празно или ако клиентът го е запазил **след** последната
  редакция на треньора във формата (`edit<id>`). Името от треньора остава. Противопоказанията само се добавят.
- Зоните за акцент (`focus<id>`) и състоянието (`cond<id>`) — на клиента, заменят се при по-нова
  версия; влизат в препоръката за тренировката (`NextPlan.individual`) и в забележката.
- Бележката на клиента отива в забележката („От клиента: …“).
- Непълен профил в PWA → при всяко отваряне прозорец „Довърши профила си“ (какво остава + „По-късно“).
- В PWA медицинските причини са един въпрос („Има ли медицинска причина…“), списъкът се отваря само при „Да“.
- Формата на таблета (`XemsLocalUserForm`): цел, форма, **Състояние**, зони за акцент; „Здраве“ е един въпрос
  (Не / Да), списъкът с противопоказания се отваря само при „Да“ („Не“ го изчиства); бележката на клиента е най-горе.
  Забележката пази фокуса, състоянието и бележката на клиента.

## Състояние → тренировката (`ai/AiPersonal`, `wearable/NextPlan.condition`)
Състоянието не спира тренировката (това правят противопоказанията) — нагласява подхода. Ключове (същите в
`server/src/profile.js` COND и в PWA):

| Група | Ключ | Ефект |
|---|---|---|
| Хормони и обмяна | `prediabetes` | бедра + седалище +10 % |
| | `pcos` | бедра + седалище +5 % |
| | `menopause` | големи мускули (бедра, седалище, гръб) +5 % |
| | `thyroid` | −5 % сила |
| | `water` | прасци −10 % (препоръка за дренаж в края) |
| | `postpartum` | корем −15 % |
| Тяло и стави | `diastasis` | корем до 40 % |
| | `back` / `neck` / `knees` | кръст / трапец −15 %, предно бедро −10 % |
| | `varicose` | прасци и задно бедро −10 % |
| | `joints` / `osteo` | −5 %, по-плавно включване (osteo и +1 s пауза) |
| Начин на живот | `desk` | гръб + седалище +5 % |
| | `senior` | големи мускули +5 %, −5 %, по-плавно, +1 s пауза |
| | `stress` / `sleep` | −5 % / −10 %, +1 s пауза (sleep и по-кратко в препоръката) |
| | `sensitive` | −10 %, по-плавно включване |
| | `injury` | само бележка за треньора |

Зона за акцент: +10 % в режимите, +5 % в препоръката. Къде влиза:
- **Автоматичен режим** — планът на всеки участник: таван на силата, паузи и включване в тетаничните стъпки,
  зони и максимум по зона; бележките се виждат в плана.
- **AI режим** — таванът на силата и паузите в плана (бележки „За този клиент“); при старта зоните на всеки
  клиент се нагласяват веднъж от неговия профил и се връщат при спиране.
- **Препоръка за следващата тренировка** (`NextPlan`) — същите правила върху последните настройки.

## Разходи (Cloudflare Workers + D1 + KV) — принципи
1. **Без таймери и фоново допитване.** Заявка тръгва само при събитие: старт на приложението, записана тренировка,
   запазен профил, резервация, дърпане надолу на първата страница на PWA (≤ 1 / 30 s).
2. **Кешът първо, източникът при промяна.** Всяко четене има евтина проверка (версия / кеш на ръба), пълното
   зареждане е само когато нещо се е променило; промяната инвалидира кеша (уебхук на Acuity, запис от таблета).
3. **Записи в базата само при промяна.** Никакъв запис за преглед; обновяването на лиценза не пише ред, ако нищо не
   се е променило (`activationStale`, ≤ 1 запис / 6 ч на таблет); лимитите на честотата са в паметта на worker-а
   (в D1 — само за активиране с ключ, срещу налучкване).
4. **Пазим това, което анализът показва, не вечен лог.** Компресиран запис само за последните 12 тренировки на клиент.
5. **Една заявка за една страница.** Анализът: 1 заявка (резюмета + записи); страницата е еднаква за всички → кеш 1 ден.

| Действие | Заявки | Хранилище |
|---|---|---|
| Клиентът запазва профила си в PWA | 1 (само при „Запази“) | D1: 1 четене + 2 записа |
| Таблетът тегли профили | само при събитие (старт; „Потребители“ / „План“ ≤ 1 / 10 мин; преди „Следващ клиент“ ≤ 1 / мин; „Синхронизирай“) | D1: 1 индексирано четене |
| Записана тренировка | 2 (картон + данни за анализа) | D1: ≈ 4 четения + 4 записа (вкл. изрязване на стари записи) |
| Клиентът отваря картона / анализа | 1 / 1 | 0 при попадение в кеша на ръба (5 мин; записът от таблета го изчиства), иначе 1–2 четения |
| PWA при влизане (от затворено или след 30 мин) | часове: 1 проверка на версията (KV четене); Acuity + 1 KV запис само ако списъкът е сменен (уебхукът го трие) или > 12 ч; картон: 1 | KV: 1 четене; D1: 1 четене |
| PWA след резервация | 1 (Acuity + 1 KV запис) | — |
| Уебхук на Acuity (резервация / промяна / отмяна) | — | KV: 1 изтриване |
| Лиценз (обновяване, код на студиото, последна версия) | ≈ 1 / ден | D1: 2–3 четения, 0–1 запис (без одит ред) |

KV (безплатно: 1000 записа / ден) е най-тясното място — затова часовете се пишат в KV само при реална промяна.
Профилите се пазят на сървъра 14 дни (всеки таблет на студиото тегли по `since`), после се трият при следващ запис.

## Кодът на студиото
`licenses.studio_code` (8 случайни знака или четим, зададен от админ панела — напр. `xbody`; публичен, id на лиценза остава скрит). Таблетът го получава при обновяване на
лиценза и го показва в „План“ → „Приложение за клиентите“. PWA го носи вграден (`XEMS_STUDIO` в `xbody.html`).
