# XEMS сървър — задание за доразработка (лицензи, функции, обновяване)

Документът описва какво е готово в приложението (клиента) и какво трябва да направи сървърът. Договорът за заявките е в [`xems-license-api.md`](xems-license-api.md); тук е цялата картина: цел, устройство, база, подписи, админ панел, издания, сигурност, стъпки за пускане.

---

## 1. Цел

1. **Отключване дистанционно:** даден таблет с XEMS получава модули и функции според ключа си. Може да се ограничи по срок и по брой устройства и може да се спре по всяко време.
2. **Обновяване на приложението:** нова версия (APK) се качва веднъж на сървъра. Таблетите я виждат, изтеглят, проверяват и инсталират.
3. **Работа без интернет:** залата може да е без мрежа. Таблетът пази подписан жетон и работи офлайн до края на лиценза + 7 дни.

---

## 2. Какво е готово в клиента (XEMS ≥ 1.1.84)

| Част | Клас | Какво прави |
|---|---|---|
| Състояние на лиценза | `widget/XemsLicense` | модули, функции, източник (код / сървър), срок, гратисен период, `device_id` |
| Жетон | `widget/XemsLicenseToken` | разчита и проверява подписа ECDSA P-256 офлайн; малък собствен JSON четец |
| Мрежа | `widget/XemsLicenseClient` | активиране, ежедневно опресняване, проверка за версия, изтегляне + SHA-256 + инсталатор |
| Настройки | `widget/XemsLicenseSection` | „Достъп и лиценз“: състояние, модули, ключ, ID на устройството, обновяване, адрес на сървъра |
| Заключване | `XemsNav`, `WearableSettingsSection`, `HrGuard`, `BandRemote`, `BandAppInstall`, `NotifyWearableBridge` | заключени плочки с 🔒 и „Нямате достъп до този модул“; гривна само при нужда |
| Функция „ръце 1:1“ | `ChannelStrengthScale.armsFactor()`, `AiEnergy.armsSent()` | ръцете се пращат ×0.05 или 1:1 според `arms_full` |

**Празни места, които се попълват при първия сървър:**
- `XemsLicense.DEFAULT_SERVER`: адресът, например `https://license.xems.bg`. Може да се въведе и в Настройки → „Сървър ›“.
- `XemsLicense.SERVER_PUBLIC_KEY`: публичният ключ на сървъра (base64 X.509). Докато е празен, клиентът не приема сървърни жетони.

**Офлайн кодове, вградени в приложението:**

| Ключ | Модули | Функции | Срок |
|---|---|---|---|
| `0123` | всички | — | без |
| `reni123` | — (базов режим) | `arms_full` | без |

Тези кодове се виждат при декомпилиране на APK. Затова са за вътрешна употреба и тестове. Когато сървърът тръгне, препоръката е:
- да се махнат от приложението или да останат само за сервиз;
- всички реални клиенти да минат на сървърни ключове.

## 3. Каталог: модули и функции

Сървърът е „изворът на истината“: той решава какво влиза в жетона.

**Модули** (`mods`), заключват екран или плочка:

| id | Име | Бележка |
|---|---|---|
| `timer` | Таймер | |
| `music` | Музика | плейър + импулси по музиката |
| `pulse` | Пулс | циферблат, автоматично намаляване на силата по пулса; включва свързване на гривната |
| `ai` | AI | умна сесия; включва свързване на гривната |
| `band` | Часовник | управление от гривната, приложение на гривната, автоматично инсталиране |

**Функции** (`feat`), включват или изключват поведение:

| id | Име | Ефект |
|---|---|---|
| `arms_full` | Ръце 1:1 | каналът за ръцете с нормална сила вместо ×0.05 |

Нови функции се добавят така: нов id в клиента (проверка с `XemsLicense.hasFeature("…")`) и в каталога на сървъра. Клиентът пренебрегва непознатите id, така че сървърът може да ги добавя преди приложението.

**Планове** (предложение; сървърът ги превежда в `mods` и `feat`):

| план | mods | feat |
|---|---|---|
| `base` | — | — |
| `pro` | timer, music, pulse | — |
| `full` | всички | — |
| по поръчка | произволни | произволни |

## 4. Устройство (предложение)

```
[Таблет XEMS] ──HTTPS/JSON──► [API: /v1/license/*, /v1/app/update]
                                   │
                                   ├── PostgreSQL / SQLite (ключове, активации, издания, журнал)
                                   ├── частен ключ ECDSA (само на сървъра, в тайно хранилище)
                                   └── хранилище за APK (S3 / диск) → HTTPS линк за изтегляне
[Админ панел (уеб)] ──► същата база: ключове, планове, издания, спиране
```

Технологията е по избор: Node/Express, Python/FastAPI, Go и др. Изискванията са малки: 3 публични заявки и един админ интерфейс.

## 5. База данни (минимум)

```sql
licenses (
  id            TEXT PRIMARY KEY,        -- "L-2026-000123" → отива в жетона като "lic"
  key_hash      TEXT UNIQUE NOT NULL,    -- SHA-256 на ключа (самият ключ не се пази)
  key_hint      TEXT,                    -- последните 4 знака за админа
  customer      TEXT,                    -- зала / клиент
  plan          TEXT,                    -- "pro", "full", …
  mods          TEXT[],                  -- ["timer","music",…]
  feat          TEXT[],                  -- ["arms_full"]
  max_devices   INT DEFAULT 1,
  expires_at    TIMESTAMP NULL,          -- NULL = без срок (exp 0 в жетона)
  status        TEXT DEFAULT 'active',   -- active | disabled | revoked
  created_at    TIMESTAMP,
  note          TEXT
)

activations (
  license_id    TEXT REFERENCES licenses(id),
  device_id     TEXT,                    -- 16 hex от клиента
  device_model  TEXT,
  android       INT,
  app_version   TEXT,
  app_code      INT,
  lang          TEXT,
  first_seen    TIMESTAMP,
  last_seen     TIMESTAMP,
  status        TEXT DEFAULT 'active',   -- active | removed (освобождава място)
  PRIMARY KEY (license_id, device_id)
)

releases (
  version_code  INT PRIMARY KEY,         -- 209
  version_name  TEXT,                    -- "1.1.84-ai"
  channel       TEXT DEFAULT 'stable',   -- stable | beta
  url           TEXT,                    -- https://… (задължително https)
  sha256        TEXT,                    -- 64 hex на APK файла
  size          BIGINT,
  notes         TEXT,                    -- кратко, показва се в приложението
  mandatory     BOOLEAN DEFAULT false,
  min_code      INT NULL,                -- по избор: от коя версия нагоре се предлага
  published_at  TIMESTAMP
)

audit (time, actor, action, license_id, device_id, detail)   -- кой какво е правил
```

## 6. Заявки (подробно в `xems-license-api.md`)

### 6.1 `POST /v1/license/activate`

**Вход:** `key`, `device_id`, `device_model`, `android`, `app_version`, `app_code`, `lang`.

**Логика:**
1. Търси `key_hash`. Ако липсва → `invalid_key`.
2. Проверява статуса: `disabled` / `revoked` → съответната грешка.
3. Проверява срока: `expires_at < now` → `expired`.
4. Ако устройството вече е активирано → обновява `last_seen` и данните му.
5. Иначе: ако активните устройства ≥ `max_devices` → `device_limit`; иначе записва нова активация.
6. Връща `{ok:true, token}` с `mods` / `feat` / `plan` / `exp` от лиценза и `dev` = `device_id`.

### 6.2 `POST /v1/license/refresh`

**Вход:** общите полета + `token`.

**Логика:**
1. Разчита `lic` от жетона (подписът се проверява със собствения ключ).
2. Търси лиценза и активацията по `lic` + `device_id`.
3. Отговори:
   - лицензът е спрян или активацията е махната → `{ok:false, error:"revoked"}` (клиентът минава в базов режим);
   - непознат лиценз → `unknown`;
   - иначе нов жетон с актуалните `mods` / `feat` / `exp`. Така промяна в админа стига до таблета до 24 часа.

### 6.3 `GET /v1/app/update?app=xems&channel=stable&code=209&device_id=…`

Връща най-новото издание от канала с `version_code > code`, или `version_code:0`, ако няма такова.

По избор: канал `beta` за избрани устройства (например по `device_id` или по лиценз).

## 7. Подпис на жетона

**Генериране на ключ (веднъж):**

```bash
openssl ecparam -name prime256v1 -genkey -noout -out xems-license-private.pem   # ПАЗИ СЕ САМО НА СЪРВЪРА
openssl ec -in xems-license-private.pem -pubout -outform DER | base64 -w0          # → SERVER_PUBLIC_KEY
```

**Жетон:**

```
payload = {"v":1,"lic":"L-2026-000123","dev":"7F3A91C20B55D1E4","plan":"pro",
           "mods":["timer","music","pulse"],"feat":[],"iat":<сега>,"exp":<край или 0>}
body    = base64url(UTF-8 JSON, без padding)
sig     = ECDSA-P256-SHA256(ASCII(body)), DER, base64url без padding
token   = body + "." + sig
```

Пример на Node.js:

```js
const crypto = require('crypto');
const b64u = b => Buffer.from(b).toString('base64url');
const body = b64u(JSON.stringify(payload));
const sig = crypto.sign('sha256', Buffer.from(body), { key: privatePem, dsaEncoding: 'der' });
const token = body + '.' + b64u(sig);
```

Какво проверява клиентът:
- подписа с `SERVER_PUBLIC_KEY`;
- дали `dev` съвпада с неговия `device_id`;
- срока `exp` + 7 дни.

Жетон с добавени модули, жетон от чуждо устройство или от чужд ключ се отхвърля. Това е проверено с тест.

**Смяна на ключа (ротация):** клиентът засега знае един публичен ключ. За бъдеща смяна:
- в жетона се добавя `"kid"`;
- в клиента се пазят два ключа — нов и стар — за периода на прехода.

Това още не е направено; добавя се при нужда.

## 8. Издания (обновяване)

1. Сглобява се APK (`build-apk.sh`) с по-голям `versionCode` (`RELEASE_VERSION`).
2. `sha256sum xems27.apk` → в `releases.sha256`.
3. APK се качва на HTTPS адрес (S3, CDN или самия сървър) → `releases.url`.
4. Записва се `notes`, а при нужда `mandatory`.
5. Таблетите виждат изданието при „Провери за нова“ в Настройки → Лиценз.

   Автоматична ежедневна проверка с известие е следваща стъпка: клиентът има `checkUpdate`, остава да се вика при старт.

**Подпис на APK:** Android приема обновление само ако е подписано със **същия сертификат** като инсталираното приложение. Всички издания трябва да се подписват с един и същ ключ; сега е debug ключът на `uber-apk-signer`. Преди истински клиенти е добре да се мине на собствен release ключ. След такава смяна обаче е нужна **една** ръчна преинсталация на всеки таблет.

## 9. Админ панел (минимум)

- **Ключове:**
  - създаване (случаен ключ във вида `XEMS-XXXX-XXXX`, показва се веднъж), избор на план, модули, функции, срок, брой устройства, клиент, бележка;
  - списък и търсене; спиране и пускане; удължаване; смяна на модули и функции (стига до таблетите при следващото опресняване, ≤ 24 ч).
- **Активации по ключ:**
  - устройство, модел, версия на приложението, последно виждане;
  - „освободи място“ (махане на устройство).
- **Издания:** качване на APK (sha256 и размер се смятат сами), бележки, канал, задължително.
- **Журнал:** кой, какво, кога.
- **Достъп до панела:** вход с парола + 2FA, отделно от публичното API.

## 10. Сигурност

- **HTTPS:** само HTTPS. Клиентът отказва адрес за изтегляне на APK, който не е `https://`.
- **Частният ключ:** само на сървъра (тайно хранилище или променлива на средата). Никога в git.
- **Ключовете:** в базата се пази само SHA-256 хеш.
- **Ограничение на опитите:** за `/activate`, например 10 опита на минута от IP и 20 на ден от `device_id`, срещу налучкване на ключове.
- **Лични данни:** жетоните не съдържат лични данни. `device_id` е хеш, а не ANDROID_ID.
- **Офлайн кодовете** (`0123`, `reni123`) са в APK: за вътрешна употреба (вж. раздел 2).

## 11. Пускане: стъпки

1. Сървър с трите заявки и базата; двойка ключове.
2. В клиента: `SERVER_PUBLIC_KEY` и `DEFAULT_SERVER` → ново издание на XEMS.
3. Тест:
   - `curl` към `/activate` с тестов ключ;
   - на таблет: Настройки → Лиценз → ключ → Активирай → модулите се отключват;
   - спиране от админа → след опресняване таблетът е в базов режим. За бърз тест опресняването може временно да се прави по-често.
4. Издание през `/v1/app/update` → „Провери за нова“ → изтегляне → инсталиране.
5. Решение за офлайн кодовете: махане или ограничаване.

## 12. Отворени решения

- **Цени и планове:** кои модули в кой план.
- **Ключовете по залата:** един ключ за няколко таблета (`max_devices`) или ключ за всеки таблет.
- **Задължително обновление:** дали `mandatory` да спира работата, докато не се обнови. Сега само се показва.
- **Автоматична проверка за обновление при старт:** клиентът я поддържа; остава да се включи.
- **Смяна на ключа за подпис** (`kid`, два ключа).
- **Собствен release сертификат на APK** преди истинските клиенти.
